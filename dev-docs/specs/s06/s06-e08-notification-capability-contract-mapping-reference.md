It does not change ADR-024, the data model, RLS, API contract, provider status, or product scope. Accepted ADRs and Project Owner direction govern architecture; applied migration source governs the database; generated `src/lib/database.types.ts` is derived evidence. This document governs only S06 implementation sequencing and mapping.

S06-02 may begin from this baseline. Section 9 records the exact applied evaluator contract and the no-further-migration boundary.

## 3. Applied notification data and invariant map

### 3.1 Canonical persistence boundary

| Artifact | Applied role | S06 rule |
| --- | --- | --- |
| `public.notification_events` | Immutable domain event with trigger, entity/project context, actor, purpose-limited payload, unique deduplication key, and occurrence timestamps | Never create a second domain event merely to represent email/WhatsApp suppression. |
| `public.notification_recipients` | Per-user/per-channel fan-out record; unique `(event_id, user_id, channel)` boundary | In-app insertion is the applied trigger point for eligible external suppression. |
| `public.whatsapp_templates` | Existing logical template metadata | WhatsApp suppression requires an active `approved` mapped template; unmapped triggers do not receive a WhatsApp row. |
| `public.notification_unread_counts_view` | Existing unread aggregate over `channel = in_app` and `read_at is null` | Remains the existing badge count source; external suppression never contributes. |
| `public.mark_notification_read(uuid)` | Self-only, in-app-only idempotent mark-read command | S06-03 uses it for one recipient row only. |
| `public.mark_all_notifications_read()` | Existing self-only in-app bulk mark-read command | S06-03 uses it for all current user unread in-app rows. |
| `private.claim_notification_batch(...)` | Future external processing lease boundary | It continues to select only `pending` or expired `processing` external rows. `suppressed` cannot be claimed. |
| `private.record_provider_receipt(...)` | Future provider receipt boundary | Returns false for a suppressed row; a receipt cannot advance terminal S06 suppression. |

### 3.2 Applied suppression invariants

A `suppressed` record is legal only when all conditions below hold:

- channel is `email` or `whatsapp`;
- `suppression_reason = provider_disabled`;
- `suppressed_at` is non-null;
- `attempt_count = 0`;
- `next_attempt_at`, claim fields, provider message/error fields, sent/delivered/read/failed timestamps are null.

A non-suppressed record has null suppression fields. Therefore no S06 route, action, or component may offer external retry, requeue, mark-read, fake provider message, receipt, or automatic later-send behavior.

## 4. Applied disabled-provider fan-out map

`private.fan_out_disabled_external_notifications()` is an `AFTER INSERT` trigger on `public.notification_recipients` restricted to inserted `in_app` rows. It consumes the existing authoritative lifecycle command's recipient selection rather than re-deriving recipients in TypeScript.

### 4.1 Eligibility and outcome

| Candidate channel | Applied eligibility | Applied result when eligible | Result when ineligible |
| --- | --- | --- | --- |
| `in_app` | Existing lifecycle command recipient selection | The source command inserts the in-app row; normal unread/read behavior applies. | No row if the source command does not select the user. |
| `email` | Recipient profile is active and not deleted; `email_notifications_enabled = true`; for a project event the user has active `project_members` row with `receives_notifications = true` | One terminal `email/suppressed/provider_disabled` row with zero attempts. | No external email row. |
| `whatsapp` | Email/project eligibility equivalent plus `whatsapp_opt_in = true`, non-null `whatsapp_consent_at`, non-null `phone_e164`, and a trigger-mapped active approved template | One terminal `whatsapp/suppressed/provider_disabled` row with the mapped `template_id` and zero attempts. | No external WhatsApp row. |

The fan-out index prevents a second same-event/user/channel row. The trigger does not run on external rows and cannot recursively fan out.

### 4.2 Applied WhatsApp template mapping

| Trigger | Logical template selected only when active/approved | WhatsApp outcome |
| --- | --- | --- |
| `deliverable_submitted` | `new_deliverable_review` | Eligible recipient gets terminal suppressed WhatsApp row. |
| `internal_review_approved` | `new_deliverable_review` | Eligible recipient gets terminal suppressed WhatsApp row. |
| `internal_changes_requested` | `changes_requested_alert` | Eligible recipient gets terminal suppressed WhatsApp row. |
| `client_changes_requested` | `changes_requested_alert` | Eligible recipient gets terminal suppressed WhatsApp row. |
| `deliverable_delivered` | `final_delivery_confirmation` | Eligible recipient gets terminal suppressed WhatsApp row. |
| Any other current trigger | no mapping | No WhatsApp row; email may still be suppressed when eligible. |

The metadata `approved` state is not Meta production activation evidence. It is only the existing local template eligibility fact. No S06 path may claim that a template was provider-approved or sent.

## 5. Current event producer and recipient mapping

The table below records the committed command behavior. “External outcome” is the applied trigger result **only when an in-app recipient is inserted**.

| Source command / workflow | Trigger and event payload fields | Existing in-app recipient selection | Applied external outcome |
| --- | --- | --- | --- |
| `transition_project_status(...)` completion/reopen path | `system`; project action/name or reopen reason | No `notification_recipients` insert in the committed source | Event-only. No in-app row means no disabled external fan-out. |
| `transition_task_status(...)` | `task_status_changed`; task title, old/new status | No `notification_recipients` insert in the committed source | Event-only. No in-app row means no disabled external fan-out. |
| `submit_deliverable_version(...)` production workflow | `deliverable_submitted`; title, version number, version ID | Active `pm_lead` and `pm_watcher` members with `receives_notifications = true` | Eligible email suppression; eligible WhatsApp suppression through `new_deliverable_review`. |
| `review_deliverable(...)` internal/client decision | `internal_review_approved`, `internal_changes_requested`, `client_review_approved`, or `client_changes_requested`; title, stage, decision, comments | Active project rows where user is deliverable assignee or PM Lead/Watcher, with `receives_notifications = true` | Eligible email suppression. WhatsApp suppression only for the three mapped template triggers; `client_review_approved` has no current WhatsApp mapping. |
| `mark_deliverable_delivered(...)` | `deliverable_delivered`; deliverable title | All active project members with `receives_notifications = true` | Eligible email suppression; eligible WhatsApp suppression through `final_delivery_confirmation`. |
| `submit_client_deliverable(...)` | `client_submission_received`; title, version number, version ID | Active `pm_lead` and `pm_watcher` members with `receives_notifications = true` | Eligible email suppression only; no WhatsApp template mapping. |
| `reopen_client_deliverable(...)` | `client_submission_reopened`; title and reason | Direct client assignee | Eligible email suppression only when project preference/profile rule passes; no WhatsApp template mapping. |
| `report_broken_link(...)` | `link_reported_broken`; title, version number, reason | Version submitter | Eligible email suppression only when project preference/profile rule passes; no WhatsApp template mapping. |

### 5.1 Producer consequences

1. S06 must not add a browser, Server Action, or component-level external recipient insertion path.
2. Event-only project/task status producers are not a defect in S06-01. They cannot produce in-app inbox or external suppression records until a separately accepted data-boundary change gives them authoritative recipients.
3. S06-03 inbox copy must derive visible category from the typed `notification_trigger`, not return/render full event payloads. This avoids exposing review comments, link-report reason, or other internal payload fields to an unintended recipient screen.
4. S06-04 queue uses only the safe aggregate function. It must not query base notification tables or event payload directly.

## 6. Applied safe read and authorization map

### 6.1 Recipient-owned inbox

| Boundary | Exact contract | Authorized caller | Forbidden exposure |
| --- | --- | --- | --- |
| `public.list_my_in_app_notifications(p_limit default 50, p_before default null)` | Bounded max 100, newest-first self-only rows returning `recipient_id`, `event_id`, trigger, entity type/id, project ID, occurred/created timestamps, read timestamp, and in-app delivery status | Any authenticated user, for `auth.uid()` only | External rows, suppression reason, provider fields, raw event payload, audit fields, other-user rows. |
| `public.mark_notification_read(p_notification_recipient_id)` | Returns boolean; updates only caller-owned row where `channel = in_app` and `read_at is null` | Owner of the in-app row | Another user’s row; external record; browser-selected status/timestamp. |
| `public.mark_all_notifications_read()` | Returns count; updates caller-owned unread `in_app` rows | Current authenticated user | External record mutation. |
| `notification_unread_counts_view` | Aggregate only for unread `in_app` rows | Existing shell server query, constrained by RLS | Suppression does not change count. |

S06-03 must use the list function and read commands through typed server-only query/action modules. It must not query `notification_events` or `notification_recipients` as a user-facing shortcut.

### 6.2 Admin/PM Lead suppressed-operation queue

| Boundary | Exact contract | Authorized caller | Returned safe representation |
| --- | --- | --- | --- |
| `public.list_suppressed_notification_operations(p_limit default 50, p_before default null)` | Bounded max 100, aggregate grouped by event/channel/status/reason | Admin globally; active `pm_lead` with `profiles.role = pm` for the associated project | Event ID, trigger, project ID/name, channel, terminal status, controlled reason, aggregate recipient count, first-created timestamp, last-suppressed timestamp. |

PM Watchers, Operators, Clients, and non-lead PM membership do not satisfy the applied function authorization. Project-null event operations are Admin-only. The function returns no recipient identity/contact data, full event payload, provider payload, raw configuration status, or secret material.

The direct table select policy now permits ordinary users only their own `in_app` rows; Admin retains existing full table access. S06-04 must consume the safe aggregate function even for Admin screens, not direct-table data.

## 8. Concrete implementation contract by succeeding work item

### S06-02 — configuration and disabled adapters

- Create server-only typed configuration under `src/lib/notifications/`.
- Use an explicit delivery mode and complete provider-specific validation; all missing/blank/placeholder/partial/invalid states are disabled.
- Disabled adapters must never instantiate Resend/Meta/QStash clients, call a provider SDK, use `fetch`, create a schedule, or manufacture a provider ID/receipt.
- UI receives only safe typed outcome codes; no provider configuration names/values cross the server boundary.

### S06-03 — recipient inbox

- Query only `list_my_in_app_notifications` and `notification_unread_counts_view` through an authenticated typed server client.
- Use `mark_notification_read` and `mark_all_notifications_read` only through a server action with narrow UUID/no-input schema and concrete locale path revalidation.
- Render generic localized trigger category text. Do not display raw event payload fields, especially comment/reason fields.
- Because the applied list function has only `p_before` timestamp and no opaque cursor, use the last returned `created_at` as the bounded pagination cursor. If same-timestamp ordering produces an observed paging ambiguity, stop and request a forward schema/function correction; do not client-deduplicate or silently skip rows.

### S06-04 — internal suppression queue

- Query only `list_suppressed_notification_operations` through a server-only internal operations module.
- Route-level authorization must reflect the database contract: Admin global; PM only where an active PM Lead project record makes queue rows visible. A generic `role = pm` route check is insufficient.
- Do not create retry, resend, requeue, provider, or recipient-detail controls.
- Use controlled `provider_disabled` display copy and aggregate count only.

### S06-05 — manual alert evaluation

**Pre-implementation prerequisite:** apply `20260822150000_s06_e08_alert_evaluation.sql` and regenerate `src/lib/database.types.ts` unchanged. After that reconciliation, S06-05 consumes only `public.evaluate_notification_alerts(p_project_id uuid default null)` through a narrow server action. It must not implement deadline/review evaluation, deduplication, recipient fan-out, or timer behavior in TypeScript.

- Admin may invoke the function globally or for a selected project.
- A PM Lead must supply a selected project and is limited by `private.is_project_lead(p_project_id)`.
- The future signed scheduler may call the same `private.evaluate_notification_alerts(...)` internal boundary through an authenticated service-role path; S06 does not configure that scheduler.
- The returned JSON is the only allowed manual-control result: evaluated task/review counts, created event count, created in-app recipient count, and created external suppression count.

### S06-06 — inactive provider-facing endpoints

- The current repository API contract must be read and reconciled before creating a route. S06-01 found no existing application implementation/consumer for provider webhook or workflow endpoints.
- A later S06-06 specification may create only the exact reserved contract paths. In inactive mode those routes must be inert, non-enumerating, and side-effect free.

### S06-07 — navigation, i18n, evidence, closeout

- Add desktop/mobile equivalent inbox navigation after S06-03 route completion.
- Do not expose internal queue navigation to every PM by application role alone; the route must handle the final project-scoped PM Lead authorization.
- Add catalog parity checks and include changed route/action/navigation tests.
- Closeout must state that external provider activation, actual sends, schedule operation, webhooks, receipts, DNS, deployment, and production verification remain deferred.

## 9. Final required S06 alert-evaluation migration

### 9.1 Authored forward migration

`supabase/migrations/20260822150000_s06_e08_alert_evaluation.sql` is the final required S06 migration source. It closes the applied-baseline evaluator gap without introducing provider activation, new external HTTP behavior, schedules, webhooks, or another schema migration requirement.

It defines:

1. `private.evaluate_notification_alerts(p_project_id uuid default null)` as the shared database-authoritative evaluator;
2. `public.evaluate_notification_alerts(p_project_id uuid default null)` as the authenticated manual/future-service entry boundary;
3. disjoint task reminder windows for `deadline_24h`, `deadline_12h`, `deadline_6h`, and one `deadline_overdue` event per task/deadline value;
4. production-only review-inactivity reminder cadence: internal review begins after three hours and repeats every three hours; client review begins after two hours and repeats every two hours; each caps at five reminders, then the deliverable becomes stalled with no sixth reminder;
5. deterministic event deduplication keys tied to task/deadline or deliverable/stage/version/review-start/reminder number;
6. authoritative recipient selection through active opted-in project membership and in-app insertion, allowing the existing S06 disabled-provider trigger to create eligible terminal email/WhatsApp suppression; and
7. client-submission exclusion from review-inactivity evaluation.

### 9.2 Applied-baseline reconciliation

The Project Owner applied the exact forward migration to `jsf-pm-dev` and regenerated `src/lib/database.types.ts` unchanged in commit `1d57a16`. The generated public function signature is `evaluate_notification_alerts(p_project_id?: string): Json`. Read-only Supabase MCP catalog inspection confirms the public/private evaluator functions and both suppression read functions exist, along with `suppressed`, `suppression_reason`, and `suppressed_at`. S06-02 may now begin.

No S06 application module may call a private function directly, reimplement reminder evaluation, select recipients, or treat the generated `Json` result as untrusted display content. S06-05 maps it to the bounded server-side aggregate result contract.

### 9.3 No further S06 migration is currently required

With the original applied suppression migration and this final alert-evaluation migration, the complete S06 plan has a database boundary for:

- terminal disabled-provider fan-out and safe recipient/internal read surfaces;
- in-app read state and unread count;
- alert evaluation, deduplication, review-inactivity caps, stalled state, and authorized manual invocation; and
- future service-role scheduler consumption of the same internal evaluator.

A later migration is not authorized merely for implementation convenience. Any further database request must be a newly discovered contradiction or a new accepted product/architecture decision, not a substitute for application implementation.
